# API specification — internal `service.py` contracts

This is not an HTTP API — the whole point of the modular-monolith
architecture (`CLAUDE.md`) is that modules talk to each other via
**direct in-process Python function calls**, not a wire protocol. This
document is the "API" in the sense that matters here: the exact,
typed function signatures each module's `service.py` exposes to its
callers.

If any of the seven modules is ever extracted into a real network
service later (`CLAUDE.md`'s "Known gaps" already anticipates this),
these signatures become the new HTTP contract more or less directly —
another reason to keep them accurate.

**Read `CLAUDE.md`'s "Applying without being a customer yet" section
first** — the account-on-approval model (most applicants aren't
customers yet; an account is the *outcome* of an approved loan, not a
precondition of filing one) is why several signatures below take
`applicant_identifier` instead of `customer_id`/`account_id`, and why
`customer_id`/`account_id` are nullable throughout.

Conventions used below:
- All functions are `async def` (matching `asyncpg`/`httpx`/`temporalio`
  all being async).
- **IDs are short, human-readable, application-assigned strings, not
  `UUID`s** — `CUS-483920174`, `ACC-019283746`, `APP-573920184`, each
  generated by `idgen.service.generate_id(prefix, 9)` (see
  `CLAUDE.md`'s "Data storage"). `workflow_id` is Temporal's own
  string id, unrelated to this scheme. Mayan `document_id`s are
  strings too, minted by Mayan itself.
- Money is `Decimal`, never `float`.
- Every dataclass shown is a plain return type (Pydantic model or
  `@dataclass` — implementer's choice, not load-bearing) mirroring its
  owning table (PRD §9).

## `idgen/service.py`

```python
def generate_id(prefix: str, length: int) -> str: ...
    # e.g. generate_id("CUS", 9) -> "CUS-483920174"
```

Pure function, zero I/O, zero state (`secrets.choice` over `0-9`). The
one function this module has — every module that assigns a primary key
(`customer/`, `account/`, `application/`, plus `bff_customer/routes.py`
for its provisional application-id pre-mint) calls it directly and
handles its own `UniqueViolationError`-on-collision retry (bounded at
10 attempts) at the insert site; `idgen/` itself has no notion of
"already used."

## `customer/service.py`

```python
async def find_by_identifier(applicant_identifier: str) -> Customer | None: ...

async def get_or_create(
    applicant_identifier: str,
    name: str | None = None,
    email: str | None = None,
    phone: str | None = None,
) -> Customer: ...

async def update_profile(
    customer_id: str,
    name: str | None,
    email: str | None,
    phone: str | None,
) -> Customer: ...

async def get(customer_id: str) -> Customer: ...
```

```python
@dataclass
class Customer:
    customer_id: str          # "CUS-483920174"
    applicant_identifier: str
    name: str | None
    email: str | None
    phone: str | None
    created_at: datetime
```

- **`find_by_identifier` is read-only** — no side effects, `None` if no
  match. Called by `application.service.create_application(...)` at
  submission time to link an application to an existing customer, and
  by `bff_customer` for "welcome back" copy and (Phase 14) form
  prefill.
- **`get_or_create` is find-or-create, idempotent — but called from
  exactly one place in the whole codebase**:
  `application/activities.py`'s `persist_decision`, at the moment an
  application resolves to terminal `APPROVED` with no customer already
  linked (`record["customer_id"] is None`). `name`/`email`/`phone`
  (Phase 14) seed the row on a genuine first create, from the
  approving application's own denormalized fields — an existing row
  (the `ON CONFLICT ... DO NOTHING` path) is never touched by this
  function no matter what's passed. `bff_customer`'s identify step does
  **not** call this — the session cookie is a pure client-side write.
- **`update_profile` (Phase 14) — a write path, called instead of
  `get_or_create` when `persist_decision` finds `customer_id` already
  set** (an existing customer's *later* application being approved).
  Unconditional overwrite, not fill-blanks-only — the most recently
  *approved* application's submitted details always win.
- `get` raises (a module-local `CustomerNotFound`) if the id doesn't
  exist.

## `account/service.py`

```python
async def create_account(
    customer_id: str,
    product_type: str,
    application_id: str,
) -> Account: ...

async def get_by_application_id(application_id: str) -> Account | None: ...

async def has_active_account_of_type(customer_id: str, product_type: str) -> bool: ...

async def get(account_id: str) -> Account: ...
```

```python
@dataclass
class Account:
    account_id: str            # "ACC-019283746"
    customer_id: str
    application_id: str        # NOT NULL, UNIQUE -- the application that produced this account
    product_type: str
    opened_at: datetime
    status: Literal["ACTIVE", "CLOSED"]
```

- **`create_account` always creates a new row — no find-or-create.**
  Accounts are 1:1 with approved applications now (`application_id` is
  `NOT NULL`/`UNIQUE`), not 1:1 with customers; a customer can hold
  many, one per approved loan. Called from exactly one place:
  `application/activities.py`'s `persist_decision`, exactly once per
  application that reaches terminal `APPROVED`.
  **`persist_decision` must check `get_by_application_id(application_id)`
  returns `None` before calling this** — Temporal can retry an activity
  after a successful-but-unacknowledged execution, and this function has
  no idempotency guard of its own. Also **not conflict-safe on its
  own** against the *business* rule — it will happily violate "one
  active account per product type" if called for a customer who already
  has one; `db/schema.sql`'s partial unique index is the backstop, not
  the primary defense (see `has_active_account_of_type` below for the
  actual, earlier gate). See `CLAUDE.md`'s "Applying without being a
  customer yet" for the full sequence.
- **`get_by_application_id` is read-only** — the reverse lookup
  `accounts.application_id`'s direction exists to make possible.
  What `persist_decision` calls first, as its idempotency check; also
  what `bff_customer`/`bff_backoffice` call to render an application's
  resulting account.
- **`has_active_account_of_type` is read-only** — the function that
  makes the active-account rule enforceable *before* a decision is
  signaled, not just inside `persist_decision`. Called by
  `application.service.check_decision_allowed(...)`, never directly by
  a BFF.

## `document/service.py`

```python
async def upload(
    applicant_identifier: str,
    application_id: str,
    category: str,
    file: UploadFile,
    customer_id: str | None = None,
) -> DocumentRef: ...

async def list_documents(application_id: str) -> list[DocumentRef]: ...

async def check_completeness(
    application_id: str,
    product_type: str,
    exclude_categories: list[str] | None = None,
) -> list[str]: ...  # missing category names, [] if satisfied

async def preview(
    application_id: str,
    document_id: str,
) -> AsyncIterator[bytes]: ...  # streamed to the BFF's response

async def has_id_photo(customer_id: str) -> bool: ...  # read-only

# Managed documents beyond the submission-gate categories above --
# all system-triggered, none uploaded by a customer through the
# application flow. See CLAUDE.md's "Applying without being a
# customer yet" and "Document metadata assignment lifecycle" for the
# full mechanics.

async def tag_application_documents(
    application_id: str,
    account_id: str,
    customer_id: str,
) -> None: ...  # attaches account_id + customer_id to every document
                # under application_id, all categories, one pass.

async def promote_government_id_to_customer_photo(
    application_id: str,
    customer_id: str,
) -> None: ...  # no-op if no fresh Government ID exists under
                # application_id (the ID-reuse path). Otherwise creates
                # a genuine SECOND Mayan document -- a customer-level
                # copy, tagged only customer_id/applicant_identifier/
                # category -- trashing any previous copy first. Does
                # NOT touch the application's own Government ID
                # document (exclusive-placement design). Called only
                # from application/activities.py's persist_decision.

async def generate_welcome_letter(
    applicant_identifier: str,
    account_id: str,
    customer_id: str,
    applicant_name: str,
    product_type: str,
    amount: Decimal,
) -> DocumentRef: ...  # renders a templated PDF and uploads it tagged
                       # to account_id + customer_id + applicant_identifier.
                       # Called only from application/activities.py's
                       # persist_decision, immediately after
                       # account.service.create_account.

async def upload_consent(
    applicant_identifier: str,
    account_id: str,
    customer_id: str,
    file: UploadFile,
) -> DocumentRef: ...  # true Mayan versioning -- uploads a new FILE
                       # VERSION of the account's one "consent"
                       # document, creating it first (with full
                       # metadata) if none exists yet. Callable by
                       # either BFF once account_id/customer_id exist.

async def preview_account_document(
    account_id: str,
    document_id: str,
) -> AsyncIterator[bytes]: ...  # account-scoped sibling of preview();
                                # needed because an account-level
                                # document carries no application_id.

async def list_customer_documents(customer_id: str) -> list[DocumentRef]: ...
async def list_account_documents(account_id: str) -> list[DocumentRef]: ...
async def list_all_documents() -> list[DocumentRef]: ...  # unfiltered,
    # used only by reconcile.py -- every document in the instance.
```

```python
@dataclass
class DocumentRef:
    document_id: str       # Mayan's own id, not a string we mint
    category: str
    filename: str
    uploaded_at: datetime
```

- **`upload`/`list_documents`/`check_completeness`/`preview` take no
  `account_id` param** — there's no `account_id` to attach at upload
  time at all (uploads happen and the completeness gate is checked
  *before* submission, before any account can exist). `upload`'s
  `customer_id` (Phase 14) is optional and caller-supplied — passed
  when the applicant already resolves to an existing customer, `None`
  otherwise; `document/` never resolves it internally, since it's a
  leaf module that never imports `application/`. See `CLAUDE.md`'s
  "Document hierarchy" for how staff browse by these fields (three
  separate entity-rooted index templates — Customer/Account/
  Application — each with **exclusive placement**: a document lives at
  exactly one leaf, the deepest entity it's actually tied to).
- `check_completeness`'s required-category list per `product_type` is
  owned here (PRD §6.4's table), not in `application/` — `application/`
  just calls this function and trusts the answer. **A category is
  satisfied by one or more documents** — `upload()` is safe to call
  repeatedly for the same `application_id`/`category`. **`exclude_categories`
  (Phase 14)** — `application.service.create_application`'s
  `reuse_existing_id_photo` path passes
  `[CATEGORY_GOVERNMENT_ID]` through it instead of requiring a fresh
  upload from a returning customer who already has one on file.
- **`check_completeness`, `list_documents`, `list_customer_documents`,
  `list_account_documents`, and `list_all_documents` must all query
  Mayan's document/metadata search API directly (filtered on the
  relevant id + category metadata), never read the Index Template
  tree.** Metadata attachment is synchronous; the *index's* tree
  membership is async (Celery — see `CLAUDE.md`'s document-hierarchy
  gotcha #2). `create_application()` calls `check_completeness()`
  synchronously right after the customer's last upload — reading the
  index tree here would risk a false "still missing" result purely
  from reindex lag, not an actual missing document.
- **`has_id_photo` (Phase 14) is read-only** — a thin wrapper over
  `list_customer_documents(customer_id)` (any result *is* the
  `id_photo`, per the one-per-customer invariant). Called by
  `application.service.create_application` to decide whether ID reuse
  is even offerable, and by `bff_customer` to decide whether to show
  the "already on file" choice.
- `tag_application_documents`, `promote_government_id_to_customer_photo`,
  and `generate_welcome_letter` are the three steps
  `application/activities.py`'s `persist_decision` runs inside its
  APPROVE-provisioning block (`CLAUDE.md`'s numbered sequence) — all
  three guarded by that same block's single idempotency check
  (`account.service.get_by_application_id(application_id) is None`
  before starting at all), not independently idempotent themselves. A
  retry that finds an account already provisioned skips all three,
  permanently — a smaller, manually-recoverable gap than a duplicated
  account.
- `generate_welcome_letter`/`upload_consent` take only plain arguments
  (no `Application`/`Customer`/`Account` objects) — `document/` stays a
  leaf module, never importing `application/`, `customer/`, or
  `account/` to look anything up itself.

## `workflow/service.py`

```python
async def start_workflow(
    application_id: str,
    product_type: str,
    payload: dict[str, Any],
    amount: Decimal,
    applicant_identifier: str,
    applicant_name: str,
    applicant_email: str,
    applicant_phone: str,
    customer_id: str | None,
) -> str: ...  # returns workflow_id

async def signal_decision(
    workflow_id: str,
    actor_role: Literal["underwriter", "manager", "customer"],
    decision: Literal["APPROVE", "REJECT", "REQUEST_MORE_INFO", "CANCELLED"],
    actor_name: str,
    comment: str | None,
) -> None: ...

async def signal_resubmit(
    workflow_id: str,
    payload: dict[str, Any],
) -> None: ...

async def bulk_signal_decision(
    workflow_ids: list[str],
    actor_role: Literal["underwriter", "manager"],
    decision: Literal["APPROVE", "REJECT"],
    actor_name: str,
    comment: str | None,
) -> list[BulkActionResult]: ...
```

```python
@dataclass
class BulkActionResult:
    workflow_id: str
    ok: bool
    error: str | None  # populated only when ok is False
```

- `amount`, `applicant_identifier`, `applicant_name`, `applicant_email`,
  `applicant_phone`, and `customer_id` all travel as their own
  arguments, never read out of `payload` — the workflow needs `amount`
  for the PRD §6.3 escalation-threshold check, and needs the rest only
  to forward them, by name, to the `persist_application` activity.
  `payload` stays product-specific-fields-only and the workflow never
  inspects any of these values itself (see `CLAUDE.md`'s note on
  `workflow/`'s "generic" framing).
- `bulk_signal_decision` takes `actor_role` (every application in one
  bulk-approve batch is decided by the same signed-in staff member, so
  it travels once per batch) and only accepts `APPROVE`/`REJECT` — bulk
  `REQUEST_MORE_INFO`/`CANCELLED` aren't UI-exposed actions.
- `_MAX_BULK_SIZE = 50` — `bulk_signal_decision` raises if
  `len(workflow_ids) > 50` rather than silently truncating.

## `application/service.py`

```python
APPLICATION_ID_PREFIX = "APP"
APPLICATION_ID_LENGTH = 9

async def create_application(
    applicant_identifier: str,
    product_type: str,
    payload: dict[str, Any],
    applicant_name: str,
    applicant_email: str,
    applicant_phone: str,
    amount: Decimal,
    application_id: str | None = None,
    reuse_existing_id_photo: bool = False,
) -> CreateApplicationResult: ...

async def resubmit_application(
    application_id: str,
    payload: dict[str, Any],
) -> Application: ...

async def check_decision_allowed(
    application_id: str,
    decision: str,
) -> list[str]: ...  # blocking-reason strings, [] if OK. No-op unless
                     # decision == "APPROVE". Called by bff_backoffice
                     # BEFORE workflow.service.signal_decision(...).

async def check_decision_allowed_bulk(
    application_ids: list[str],
    decision: str,
) -> dict[str, list[str]]: ...  # application_id -> blocking reasons
    # ([] entries omitted or empty). Batch-aware sibling of the above --
    # tracks (applicant_identifier, product_type) pairs an earlier,
    # still-eligible item in the SAME batch already claimed, closing
    # the in-batch half of the active-account race window. Called by
    # bff_backoffice's bulk-approve route instead of looping the
    # single-item function.

async def get(application_id: str) -> Application: ...

async def list_for_applicant(
    applicant_identifier: str,
    page: int,
    page_size: int = 10,
    query_id: str | None = None,
) -> PagedResult[Application]: ...

async def list_by_status(
    status: str,
    page: int,
    page_size: int = 10,
    query_id: str | None = None,
) -> PagedResult[Application]: ...
```

```python
@dataclass
class CreateApplicationResult:
    application_id: str                    # always present, even when application is None
    application: Application | None        # None if documents were missing
    missing_categories: list[str]          # [] if application was created

@dataclass
class Application:
    application_id: str            # "APP-573920184"
    applicant_identifier: str
    customer_id: str | None        # None until an existing customer is matched, or until approval
    # NOTE: no account_id field here -- accounts.application_id points
    # the other way; use account.service.get_by_application_id(...).
    workflow_id: str | None
    product_type: str
    payload: dict[str, Any]
    applicant_name: str
    applicant_email: str
    applicant_phone: str
    amount: Decimal
    status: str
    underwriter_name: str | None
    underwriter_comment: str | None
    underwriter_decided_at: datetime | None
    manager_name: str | None
    manager_comment: str | None
    manager_decided_at: datetime | None
    created_at: datetime
    updated_at: datetime

@dataclass
class PagedResult(Generic[T]):
    items: list[T]
    query_id: str
    total_count: int
    page: int
    page_size: int
```

- **No `customer_id`/`account_id` params on `create_application`** —
  neither is guaranteed to exist yet, and there is no `account_id`
  column on `applications` at all. **`application_id` is optional** —
  `bff_customer` mints a provisional id up front
  (`idgen.service.generate_id(APPLICATION_ID_PREFIX,
  APPLICATION_ID_LENGTH)`) and threads it through every
  `document.service.upload(...)` call during its wizard *before*
  calling this function, so this function accepts and reuses that id
  verbatim rather than minting its own; if omitted, it mints a fresh
  one itself the same way. **The result always carries
  `application_id`**, even in the missing-categories branch (which
  persists no row), so a caller can learn what id its just-checked
  documents were tagged under and retry once they're uploaded.
  Resolves `customer_id` via the **read-only**
  `customer.service.find_by_identifier(applicant_identifier)`, validates
  `payload` against `product_type`'s schema, calls
  `document.service.check_completeness(...)` (with
  `exclude_categories=[CATEGORY_GOVERNMENT_ID]` when
  `reuse_existing_id_photo=True` and the applicant both resolves to a
  customer and `document.service.has_id_photo(customer_id)` is `True`
  — Phase 14). Never calls `workflow.service` when documents are
  missing.
- **`resubmit_application` does not take `reuse_existing_id_photo`** —
  deliberately deferred, see `PRD.md` §11.
- **`list_for_applicant` takes `applicant_identifier`, not
  `customer_id`** — this has to return an applicant's own applications
  even before any of them are approved and `customer_id` gets resolved.
  A `query_id` minted for one `applicant_identifier` must be
  rejected/ignored if reused with a different one — this is the actual
  mechanism enforcing "a customer only ever sees their own
  applications" (PRD §10 success criterion 2), not a UI-level filter.
- **`check_decision_allowed` resolves `customer_id`, then calls
  `account.service.has_active_account_of_type(customer_id,
  product_type)`** — both read-only. **Resolves via
  `customer.service.find_by_identifier(...)` when the row's own
  `customer_id` is still `NULL`**, not just trusting the column (a
  since-approved sibling application under the same identifier may have
  already resolved one — trusting `NULL` alone was a real bug, found
  live in P13-7 and fixed). `bff_backoffice` calls this before
  signaling a single-item Approve decision; see `CLAUDE.md`'s "Applying
  without being a customer yet" for the full active-account rule,
  including its accepted, narrower (cross-request only) race-window
  gap.

### `application/activities.py` — the Temporal activity contract

Not called directly by any BFF — invoked by `workflow/workflows.py`
**by string name** (see `CLAUDE.md`'s "Breaking the cycle"). Listed
here because the string name + argument shape *is* a contract between
`workflow/` and `application/`, even though it's not a normal function
call. **This is also the one file in `application/` allowed to import
`customer/` and `account/`** — see `CLAUDE.md`'s "Applying without
being a customer yet".

```python
@activity.defn(name="persist_application")
async def persist_application(
    application_id: str,
    applicant_identifier: str,
    customer_id: str | None,
    workflow_id: str,
    product_type: str,
    payload: dict[str, Any],
    applicant_name: str,
    applicant_email: str,
    applicant_phone: str,
    amount: Decimal,
) -> None: ...  # INSERTs the applications row -- first step of run().

@activity.defn(name="persist_decision")
async def persist_decision(
    application_id: str,
    new_status: str,
    actor_role: Literal["underwriter", "manager", "customer", "temporal-admin"],
    decision: str,
    actor_name: str,
    comment: str | None,
) -> str: ...  # returns the status ACTUALLY written -- see the
               # conflict-to-REJECTED note below. workflows.py's
               # submit_decision uses this return value (not its own
               # pre-computed resulting_status) for self._status.
```

`persist_decision` handles all four decision outcomes
(APPROVE/REJECT/REQUEST_MORE_INFO/CANCELLED) in one activity, writing
`underwriter_name`/`underwriter_comment`/`underwriter_decided_at` or
`manager_name`/`manager_comment`/`manager_decided_at` depending on
`actor_role` — same activity, column choice branches on the argument.

**When `new_status == "APPROVED"`** (a terminal approval — the
Underwriter's below-threshold approve, or the Manager's approve after
escalation; *not* the intermediate `PENDING_MANAGER_APPROVAL` step),
`persist_decision` additionally:

1. Calls `account.service.get_by_application_id(application_id)`. A
   non-`None` result means this is a Temporal retry of an
   already-provisioned application — skip straight to step 5 below,
   using the existing account's `customer_id`.
2. If `applications.customer_id` is still `NULL`, calls
   `customer.service.get_or_create(applicant_identifier, name, email,
   phone) -> Customer`; otherwise calls
   `customer.service.update_profile(customer_id, name, email, phone)`
   (Phase 14 — branches on whether a customer already existed).
3. Calls `account.service.create_account(customer_id, product_type,
   application_id) -> Account`. Not conflict-checked again here —
   `check_decision_allowed`/`check_decision_allowed_bulk` already ran
   before this decision was ever signaled; this call trusts that, with
   `db/schema.sql`'s partial unique index as the backstop against the
   accepted, documented race window. **If this insert hits that
   constraint** (the race window was actually hit), `persist_decision`
   catches the specific `UniqueViolationError` and converts the whole
   decision into a clean `REJECTED` write instead of letting the
   exception propagate — see `CLAUDE.md`'s "Known gaps" for the full
   mechanism.
4. Calls `document.service.tag_application_documents(application_id,
   account_id, customer_id)`,
   `document.service.promote_government_id_to_customer_photo(application_id,
   customer_id)`, and
   `document.service.generate_welcome_letter(applicant_identifier,
   account_id, customer_id, applicant_name, product_type, amount)`.
5. Writes `status`, the decision columns, and `customer_id` (`COALESCE`d
   — harmless if already set). There is no `account_id` column on
   `applications` to write.

```python
@activity.defn(name="persist_resubmit")
async def persist_resubmit(
    application_id: str,
    payload: dict[str, Any],
) -> None: ...  # sets status back to PENDING_UNDERWRITING, updates payload
```

## Cross-cutting: `reconcile.py`

Not a `service.py` — a composition-root script (see `CLAUDE.md`'s
"Document/database reconciliation"), the only file besides `app.py`/
`worker_main.py` allowed to import every domain module. Calls
`document.service.list_all_documents()` plus each owning module's
`get(...)` (catching `NotFound`) to detect orphaned documents and stale
`customer_id` tags; `--fix` moves orphans to Mayan's trash and strips
stale tags. No public `service.py` functions of its own to document
here — see `CLAUDE.md` for the full detection/fix logic.
