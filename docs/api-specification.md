# API specification — internal `service.py` contracts

This is not an HTTP API — the whole point of the modular-monolith
architecture (`CLAUDE.md`) is that modules talk to each other via
**direct in-process Python function calls**, not a wire protocol. This
document is the "API" in the sense that matters here: the exact,
typed function signatures each module's `service.py` exposes to its
callers.

**Every signature below is copied from (or directly derived from) the
real code in `loan_onboarding/`, not from `CLAUDE.md`'s prose** — this
file previously drifted from the shipped contracts more than once (see
"Status" at the bottom), so this pass re-derived everything directly
from source rather than from the architecture doc's descriptions of it.

If any of the seven built modules (plus the planned eighth, `risk/`)
is ever extracted into a real network service later (`CLAUDE.md`'s
"Known gaps" already anticipates this), these signatures become the
new HTTP contract more or less directly — another reason to keep them
accurate.

**Read `CLAUDE.md`'s "Applying without being a customer yet" section
first** — the account-on-approval model (most applicants aren't
customers yet; an account is the *outcome* of an approved loan, not a
precondition of filing one) is why several signatures below take
`applicant_identifier` instead of `customer_id`/`account_id`, and why
`customer_id`/`account_id` are nullable throughout.

Conventions used below:
- All functions are `async def` unless marked otherwise (`idgen/` and
  `notifications/` are plain sync functions — no I/O in the first case,
  deliberately blocking `smtplib` calls in the second, since nothing in
  this codebase currently needs the email send itself to be
  non-blocking).
- **IDs are short, human-readable, application-assigned strings, not
  `UUID`s** — `CUS-483920174`, `ACC-019283746`, `APP-573920184`, each
  generated by `idgen.service.generate_id(prefix, 9)` (see
  `CLAUDE.md`'s "Data storage"). `workflow_id` is Temporal's own
  string id, unrelated to this scheme. **Mayan `document_id`s are
  `int`, not `str`** — minted by Mayan itself, exposed as-is.
- **Money is `Decimal` at the `application/`/`customer`-facing
  boundary, but narrows to `float`/`str` crossing into `workflow/`/
  `document/`/`notifications/`** — a real, deliberate inconsistency,
  not a typo: `application.service.create_application`'s `amount:
  Decimal` is converted to `float(amount)` before
  `workflow.service.start_workflow` (whose own signature takes
  `amount: float`, and which forwards it to `ApplicationWorkflowInput`/
  `PersistApplicationInput`, also `float`); `document.service.generate_welcome_letter`
  and `notifications.service.send_welcome_letter_email`/
  `send_account_closure_decision` take `amount`/money fields as `str`
  (they only ever interpolate it into rendered text, never do
  arithmetic on it). If this ever needs fixing for real precision
  reasons, it's a `workflow/`/`document/`/`notifications/`-side change,
  not an `application/`-side one.
- Every dataclass shown is copied from the module's own `models.py` (or
  `workflows.py` for the two Temporal activity-input dataclasses) —
  `frozen=True` unless noted.

## `idgen/service.py`

```python
def generate_id(prefix: str, length: int) -> str: ...
    # e.g. generate_id("CUS", 9) -> "CUS-483920174"
```

Pure function, zero I/O, zero state (`secrets.choice` over `0-9`). The
one function this module has — every module that assigns a primary key
(`customer/`, `account/`, `application/`, plus `bff_customer/routes.py`
for its provisional application-id pre-mint) calls it directly and
handles its own `UniqueViolationError`-on-collision retry (bounded at
10 attempts) at the insert site; `idgen/` itself has no notion of
"already used."

## `customer/service.py`

```python
async def find_by_identifier(applicant_identifier: str) -> Customer | None: ...

async def get_or_create(
    applicant_identifier: str,
    name: str | None = None,
    email: str | None = None,
    phone: str | None = None,
) -> Customer: ...

async def update_profile(
    customer_id: str,
    name: str | None,
    email: str | None,
    phone: str | None,
) -> Customer: ...

async def get(customer_id: str) -> Customer: ...
```

```python
@dataclass(frozen=True, slots=True)
class Customer:
    customer_id: str          # "CUS-483920174"
    applicant_identifier: str
    name: str | None
    email: str | None
    phone: str | None
    created_at: datetime
```

- **`find_by_identifier` is read-only** — no side effects, `None` if no
  match. Called by `application.service.create_application(...)` at
  submission time to link an application to an existing customer, and
  by `bff_customer` for "welcome back" copy and form prefill.
- **`get_or_create` is find-or-create, idempotent — but called from
  exactly one place in the whole codebase**:
  `application/activities.py`'s `persist_decision`, at the moment an
  application resolves to terminal `APPROVED` with no customer already
  linked. `name`/`email`/`phone` seed the row on a genuine first
  create, from the approving application's own denormalized fields —
  an existing row (the `ON CONFLICT ... DO NOTHING` path) is never
  touched by this function no matter what's passed. `bff_customer`'s
  identify step does **not** call this — the session cookie is a pure
  client-side write.
- **`update_profile` — a write path, called instead of `get_or_create`
  when `persist_decision` finds `customer_id` already set** (an
  existing customer's *later* application being approved).
  Unconditional overwrite, not fill-blanks-only — the most recently
  *approved* application's submitted details always win.
- `get` raises `CustomerNotFound` if the id doesn't exist.

## `account/service.py`

```python
async def create_account(
    customer_id: str,
    product_type: str,
    application_id: str,
) -> Account: ...

async def get_by_application_id(application_id: str) -> Account | None: ...

async def has_active_account_of_type(customer_id: str, product_type: str) -> bool: ...

async def get(account_id: str) -> Account: ...

async def request_closure(account_id: str, applicant_identifier: str) -> str: ...
    # returns workflow_id; raises AccountNotActive if status != "ACTIVE"

async def list_pending_closure_requests() -> list[Account]: ...
    # read-only; every account currently CLOSURE_REQUESTED, unpaginated

async def wait_for_status_change(account_id: str, previous_status: str) -> Account: ...
```

```python
@dataclass(frozen=True, slots=True)
class Account:
    account_id: str             # "ACC-019283746"
    customer_id: str
    application_id: str         # NOT NULL, UNIQUE -- the application that produced this account
    product_type: str
    opened_at: datetime
    status: Literal["ACTIVE", "CLOSURE_REQUESTED", "CLOSED"]
    # Closure request/decision tracking (built, Phase 18 -- see
    # CLAUDE.md's "Account closure"). All None until a closure is ever
    # requested; only the *current* request's data is kept -- a second
    # request after a rejection overwrites these rather than preserving
    # history.
    closure_workflow_id: str | None = None
    closure_requested_at: datetime | None = None
    closure_decision_comment: str | None = None
    closure_decided_by: str | None = None
    closure_decided_at: datetime | None = None
```

- **`create_account` always creates a new row — no find-or-create.**
  Accounts are 1:1 with approved applications now (`application_id` is
  `NOT NULL`/`UNIQUE`), not 1:1 with customers; a customer can hold
  many, one per approved loan. Called from exactly one place:
  `application/activities.py`'s `persist_decision`, exactly once per
  application that reaches terminal `APPROVED`.
  **`persist_decision` must check `get_by_application_id(application_id)`
  returns `None` before calling this** — Temporal can retry an activity
  after a successful-but-unacknowledged execution, and this function has
  no idempotency guard of its own. Also **not conflict-safe on its
  own** against the *business* rule — it will happily violate "one
  active account per product type" if called for a customer who already
  has one; `db/schema.sql`'s partial unique index is the backstop, not
  the primary defense (see `has_active_account_of_type` below for the
  actual, earlier gate).
- **`get_by_application_id` is read-only** — the reverse lookup
  `accounts.application_id`'s direction exists to make possible.
  What `persist_decision` calls first, as its idempotency check; also
  what `bff_customer`/`bff_backoffice` call to render an application's
  resulting account.
- **`has_active_account_of_type` is read-only** — the function that
  makes the active-account rule enforceable *before* a decision is
  signaled, not just inside `persist_decision`. Called by
  `application.service.check_decision_allowed(...)` and
  `application.service.get_available_product_types(...)`, never
  directly by a BFF.
- **`request_closure` (built, Phase 18) starts `CloseAccountWorkflow`**
  via `workflow.service.start_close_account_workflow(...)`, then blocks
  until `persist_closure_request` actually commits
  (`status == "CLOSURE_REQUESTED"`) before returning — same
  `_wait_until()`-confirm-then-return pattern
  `application.service.create_application` uses. Raises
  `AccountNotActive` if the account isn't currently `ACTIVE` — same "the
  UI hides it, the service still enforces it" discipline
  `application.service`'s product-type picker follows. **`applicant_identifier`
  is an opaque pass-through, never resolved internally** — `account/`
  still doesn't import `customer/`; the caller (`bff_customer`, which
  already holds this value from its own session cookie) supplies it so
  `persist_closure_decision` (`account/activities.py`) can eventually
  forward it to `notifications.service.send_account_closure_decision`.
- **`list_pending_closure_requests` is read-only** — backs
  `bff_backoffice`'s closure-request queue screen. Deliberately
  **unpaginated**, unlike `application.service.list_by_status`'s own
  count-cache-backed queues — a closure request is expected to be rare
  enough at POC scale.
- **`wait_for_status_change`** polls until `status` no longer equals
  `previous_status` or times out — same role
  `application.service.wait_for_status_change` plays for applications:
  `workflow.service.signal_close_account_decision`/
  `signal_close_account_cancel` only confirm Temporal *accepted* the
  signal, so a caller that immediately wants to show the post-decision
  state needs this. Always returns the current `Account`, even on
  timeout.

### `account/activities.py` — the Temporal activity contract (built, Phase 18)

Not called directly by any BFF — invoked by `workflow/workflows.py`'s
`CloseAccountWorkflow` **by string name** (same "Breaking the cycle"
split `application/activities.py` established for
`LoanApplicationWorkflow`). **This is the one file in `account/`
allowed to import `notifications/`** (plus `workflow/workflows.py`'s
own dataclasses) — `customer/` stays off-limits here, same as
everywhere else in `account/`.

```python
@activity.defn
async def persist_closure_request(inp: PersistClosureRequestInput) -> None: ...

@activity.defn
async def persist_closure_decision(inp: PersistClosureDecisionInput) -> str: ...
    # returns the status ACTUALLY written -- workflows.py's
    # submit_decision/cancel use this (not their own pre-computed
    # resulting_status) as the workflow's own self._status.
```

```python
@dataclass
class PersistClosureRequestInput:
    account_id: str
    workflow_id: str

@dataclass
class PersistClosureDecisionInput:
    account_id: str
    applicant_identifier: str
    decision: str            # APPROVE | REJECT | CANCELLED
    actor_name: str
    comment: str
    resulting_status: str    # CLOSED | ACTIVE
```

- **Idempotency guard**: if the account's status has already moved past
  `CLOSURE_REQUESTED` when `persist_closure_decision` runs (a retry of
  an already-decided execution), it returns the already-written status
  without writing again or re-sending the email — a duplicate
  closure-decision email would otherwise be a real, customer-visible
  side effect of a Temporal retry. Same "check current state before
  redoing a side effect" discipline `application/activities.py`'s own
  `persist_decision` uses.
- **`persist_closure_decision` calls
  `notifications.service.send_account_closure_decision(...)`
  unconditionally on every real (non-retry) decision** — see
  `notifications/service.py` below for the fake-vs-real delivery split.

## `notifications/service.py` (built, Phase 18/20)

A shared leaf module — same "zero dependency on anything else in this
codebase" shape as `idgen/`. Promoted out of `bff_customer/notifications.py`
so a Temporal *activity* (not just a BFF route handler) can send an
email. **All three functions are plain synchronous `def`, not `async
def`** — the only I/O they do is a blocking `smtplib` call, and nothing
in this codebase currently needs that call to be non-blocking.

```python
def send_verification_code(applicant_identifier: str, code: str) -> None: ...
    # ALWAYS fake -- print()s the code, never sent via SMTP even when
    # configured. See its own docstring: the verify-code page shows the
    # code directly in its own response, so real-only delivery here
    # would remove the only way a tester without real inbox access can
    # complete the identify flow at all.

def send_account_closure_decision(
    applicant_identifier: str,
    account_id: str,
    product_type: str,
    decision: str,
    comment: str,
) -> None: ...
    # Called only from account/activities.py's persist_closure_decision.

def send_welcome_letter_email(
    applicant_identifier: str,
    account_id: str,
    product_type: str,
    amount: str,
) -> None: ...
    # Called only from application/activities.py's persist_decision,
    # inside the same existing_account-is-None provisioning block that
    # calls document.service.generate_welcome_letter(...).
```

- **Fake by default, real delivery optional (built, Phase 20)** — both
  `send_account_closure_decision`/`send_welcome_letter_email` go
  through a private `_send_email(to_address, subject, body)` helper: it
  sends a real email via `smtplib` (`starttls()` + `login()` +
  `send_message()`) when both `SMTP_USERNAME`/`SMTP_PASSWORD` env vars
  are set (a Gmail account + an App Password, in the common case — see
  `.env.example`; `SMTP_HOST` defaults to `smtp.gmail.com`, `SMTP_PORT`
  to `587`, `SMTP_FROM_ADDRESS` defaults to `SMTP_USERNAME`), and falls
  through to the exact same fake `print()` behavior this module always
  had, byte-for-byte, when either is unset. Zero new dependencies —
  `smtplib`/`email` are Python stdlib.
- **A real send failure is caught inside `_send_email` and logged via
  `print(...)`, never raised** — both call sites sit inside Temporal
  activities whose other provisioning calls already accept "a retry
  skips this permanently, once the account/decision is already
  committed" as a smaller, more recoverable gap than letting a
  transient failure retry the whole activity.
- **Recipient is `applicant_identifier` itself** — no separate "email
  address" parameter anywhere in this module; `bff_customer`'s identify
  flow has only ever accepted an email address, so the same value
  already threaded through every function's signature *is* the address
  to send to.

## `document/service.py`

```python
async def upload(
    applicant_identifier: str,
    application_id: str,
    category: str,
    file: UploadedFile,
    customer_id: str | None = None,
) -> DocumentRef: ...

async def list_documents(application_id: str) -> list[DocumentRef]: ...

async def list_all_documents() -> list[DocumentRef]: ...
    # unfiltered -- used only by reconcile.py

async def check_completeness(
    application_id: str,
    product_type: str,
    exclude_categories: list[str] | None = None,
) -> list[str]: ...  # missing category names, [] if satisfied

async def preview(application_id: str, document_id: int) -> DocumentStream: ...
async def preview_account_document(account_id: str, document_id: int) -> DocumentStream: ...

async def has_id_photo(customer_id: str) -> bool: ...  # read-only

# Managed documents beyond the submission-gate categories above --
# all system-triggered, none uploaded by a customer through the
# application flow. See CLAUDE.md's "Applying without being a
# customer yet" and "Document metadata assignment lifecycle" for the
# full mechanics.

async def tag_application_documents(
    application_id: str,
    account_id: str,
    customer_id: str,
) -> None: ...  # attaches account_id + customer_id to every document
                # under application_id, all categories, one pass.

async def promote_government_id_to_customer_photo(
    application_id: str,
    customer_id: str,
) -> None: ...  # no-op if no fresh Government ID exists under
                # application_id (the ID-reuse path). Otherwise creates
                # a genuine SECOND Mayan document -- a customer-level
                # copy, tagged only customer_id/applicant_identifier/
                # category -- trashing any previous copy first. Does
                # NOT touch the application's own Government ID
                # document (exclusive-placement design). Called only
                # from application/activities.py's persist_decision.

async def generate_welcome_letter(
    applicant_identifier: str,
    account_id: str,
    customer_id: str,
    applicant_name: str,
    product_type: str,
    amount: str,
) -> DocumentRef: ...  # renders a templated PDF and uploads it tagged
                       # to account_id + customer_id + applicant_identifier.
                       # Called only from application/activities.py's
                       # persist_decision, immediately after
                       # account.service.create_account.

async def upload_consent(
    applicant_identifier: str,
    account_id: str,
    customer_id: str,
    file: UploadedFile,
) -> DocumentRef: ...  # true Mayan versioning -- uploads a new FILE
                       # VERSION of the account's one "consent"
                       # document, creating it first (with full
                       # metadata) if none exists yet. Callable by
                       # either BFF once account_id/customer_id exist.

async def list_customer_documents(customer_id: str) -> list[DocumentRef]: ...
async def list_account_documents(account_id: str) -> list[DocumentRef]: ...
```

```python
@dataclass(frozen=True)
class UploadedFile:
    """What a caller (a BFF route) hands upload()/upload_consent() --
    deliberately not a FastAPI UploadFile or any web-framework type,
    since document/ doesn't depend on one."""
    filename: str
    content: bytes

@dataclass(frozen=True)
class DocumentRef:
    document_id: int          # Mayan's own id -- an int, not a string we mint
    filename: str
    category: str | None
    applicant_identifier: str | None = None
    application_id: str | None = None
    account_id: str | None = None
    customer_id: str | None = None

@dataclass(frozen=True)
class DocumentStream:
    """A caller reads content_type/filename for response headers and
    iterates aiter_bytes(); must always call aclose() when done
    (success or error) -- same contract as httpx.Response(stream=True),
    which this wraps."""
    filename: str
    content_type: str
    aiter_bytes: Callable[[], AsyncIterator[bytes]]
    aclose: Callable[[], Awaitable[None]]
```

- **`upload`/`list_documents`/`check_completeness`/`preview` take no
  `account_id` param** — there's no `account_id` to attach at upload
  time at all (uploads happen and the completeness gate is checked
  *before* submission, before any account can exist). `upload`'s
  `customer_id` is optional and caller-supplied — passed when the
  applicant already resolves to an existing customer, `None`
  otherwise; `document/` never resolves it internally, since it's a
  leaf module that never imports `application/`. See `CLAUDE.md`'s
  "Document hierarchy" for how staff browse by these fields (three
  separate entity-rooted index templates — Customer/Account/
  Application — each with **exclusive placement**: a document lives at
  exactly one leaf, the deepest entity it's actually tied to).
- `check_completeness`'s required-category list per `product_type` is
  owned here (PRD §6.4's table), not in `application/` — `application/`
  just calls this function and trusts the answer. **A category is
  satisfied by one or more documents** — `upload()` is safe to call
  repeatedly for the same `application_id`/`category`. `exclude_categories`
  is what `application.service.create_application`'s
  `reuse_existing_id_photo` path passes `[CATEGORY_GOVERNMENT_ID]`
  through, instead of requiring a fresh upload from a returning
  customer who already has one on file.
- **`check_completeness`/`list_documents`/`list_customer_documents`/
  `list_account_documents`/`list_all_documents` must all query Mayan's
  document/metadata search API directly (filtered on the relevant id +
  category metadata), never read the Index Template tree.** Metadata
  attachment is synchronous; the *index's* tree membership is async
  (Celery — see `CLAUDE.md`'s document-hierarchy gotcha #2).
  `create_application()` calls `check_completeness()` synchronously
  right after the customer's last upload — reading the index tree here
  would risk a false "still missing" result purely from reindex lag,
  not an actual missing document.
- **`preview`/`preview_account_document` verify ownership from real
  Mayan metadata before streaming, not from trusting the caller's URL**
  — `preview` checks `application_id`, `preview_account_document`
  checks `account_id`; both raise `DocumentNotFound` on a mismatch,
  both share the actual streaming call via a private `_stream_document`
  helper.
- **`has_id_photo` is read-only** — a thin wrapper over
  `list_customer_documents(customer_id)` (any result *is* the
  `id_photo`, per the one-per-customer invariant). Called by
  `application.service.create_application` to decide whether ID reuse
  is even offerable, and by `bff_customer` to decide whether to show
  the "already on file" choice.
- `tag_application_documents`, `promote_government_id_to_customer_photo`,
  and `generate_welcome_letter` are three of the four steps
  `application/activities.py`'s `persist_decision` runs inside its
  APPROVE-provisioning block (the fourth, built Phase 19, is
  `notifications.service.send_welcome_letter_email` — see below) — all
  guarded by that same block's single idempotency check
  (`account.service.get_by_application_id(application_id) is None`
  before starting at all), not independently idempotent themselves. A
  retry that finds an account already provisioned skips all four,
  permanently — a smaller, manually-recoverable gap than a duplicated
  account.
- `generate_welcome_letter`/`upload_consent` take only plain arguments
  (no `Application`/`Customer`/`Account` objects) — `document/` stays a
  leaf module, never importing `application/`, `customer/`, or
  `account/` to look anything up itself.

## `workflow/service.py`

**Every function here takes an explicit `client: Client` (a
`temporalio.client.Client`) as its first parameter** — `workflow/`
holds no Temporal client of its own; the caller (`application/service.py`,
`account/service.py`, or a BFF route) is responsible for getting one.

```python
async def start_workflow(
    client: Client,
    application_id: str,
    product_type: str,
    payload: dict[str, Any],
    amount: float,
    applicant_identifier: str,
    applicant_name: str,
    applicant_email: str,
    applicant_phone: str,
    customer_id: str | None = None,
) -> str: ...  # returns workflow_id

async def signal_decision(
    client: Client,
    workflow_id: str,
    actor_role: str,
    decision: str,
    actor_name: str,
    comment: str = "",
) -> None: ...

async def signal_resubmit(
    client: Client,
    workflow_id: str,
    payload: dict[str, Any],
) -> None: ...

async def bulk_signal_decision(
    client: Client,
    workflow_ids: list[str],
    actor_role: str,
    decision: str,
    actor_name: str,
    comment: str = "",
) -> list[BulkActionResult]: ...

# CloseAccountWorkflow (built, Phase 18 -- see CLAUDE.md's "Account closure")

async def start_close_account_workflow(
    client: Client,
    account_id: str,
    applicant_identifier: str,
) -> str: ...  # returns workflow_id; called only by account.service.request_closure

async def signal_close_account_decision(
    client: Client,
    workflow_id: str,
    actor_role: str,          # "underwriter" | "manager" only -- no escalation tier
    decision: str,             # "APPROVE" | "REJECT" only
    actor_name: str,
    comment: str = "",
) -> None: ...  # called by bff_backoffice's closure-review screen

async def signal_close_account_cancel(client: Client, workflow_id: str) -> None: ...
    # called only by bff_customer, while the request is still pending
```

```python
@dataclass
class BulkActionResult:
    workflow_id: str
    ok: bool
    error: str | None = None  # populated only when ok is False
```

- `amount`, `applicant_identifier`, `applicant_name`, `applicant_email`,
  `applicant_phone`, and `customer_id` all travel as their own
  arguments, never read out of `payload` — the workflow needs `amount`
  for the PRD §6.3 escalation-threshold check, and needs the rest only
  to forward them, by name, to the `persist_application` activity.
  `payload` stays product-specific-fields-only and the workflow never
  inspects any of these values itself.
- `start_workflow`/`start_close_account_workflow` only confirm Temporal
  *accepted* the start, never that the first activity
  (`persist_application`/`persist_closure_request`) has actually
  committed — the caller (`application.service.create_application`/
  `account.service.request_closure`) polls its own read path
  (`_wait_until()`) for that.
- `bulk_signal_decision` takes `actor_role` (every application in one
  bulk-approve batch is decided by the same signed-in staff member, so
  it travels once per batch); `_validate_bulk_ids` raises on an empty
  list or more than `_MAX_BULK_SIZE = 50` ids (deduped first, order
  preserved) rather than silently truncating.
- **`signal_close_account_decision` validates `actor_role`/`decision`
  against a narrower set than `signal_decision`** —
  `{"underwriter", "manager"}` / `{"APPROVE", "REJECT"}` only, both
  raising `ValueError` otherwise; the customer's own decision path is
  `signal_close_account_cancel`, a separate signal
  (`CloseAccountWorkflow.cancel`, no arguments), not a `decision` value
  on this function.
- `_workflow_id_for_application`/`_workflow_id_for_account_closure` are
  both deterministic, not a fresh id per call — `loan-application-<application_id>`
  / `account-closure-<account_id>` — safe to reuse because a new start
  is only ever attempted once the previous execution under that same id
  has already reached a terminal state (Temporal's default
  `WorkflowIDReusePolicy.ALLOW_DUPLICATE` permits this).

    always present, even in the missing-categories branch (which

    learn what id its just-checked documents should be tagged under."""

    missing_categories: list[str]

    application_id: str            # "APP-573920184"
    applicant_identifier: str
    customer_id: str | None        # None until an existing customer is matched, or until approval
    # NOTE: no account_id field here -- accounts.application_id points
    # the other way; use account.service.get_by_application_id(...).
    workflow_id: str | None
    product_type: str
    payload: dict[str, Any]

    applicant_email: str
    applicant_phone: str

    manager_comment: str | None

    updated_at: datetime

- **`get_available_product_types` is the proactive half of the
  active-account rule** — reuses the same
  `account.service.has_active_account_of_type` read
  `check_decision_allowed` relies on, so the two can never disagree.
  **UX-only, not a new enforcement path**: a customer who bypasses this
  filter (a direct POST past the picker) still gets caught at
  `check_decision_allowed`, converted to a clean `REJECTED` outcome on
  approval, never silently succeeding.
- **No `customer_id`/`account_id` params on `create_application`** —
  neither is guaranteed to exist yet, and there is no `account_id`
  column on `applications` at all. **`application_id` is optional** —
  `bff_customer` mints a provisional id up front and threads it through
  every `document.service.upload(...)` call during its wizard *before*
  calling this function, so this function accepts and reuses that id
  verbatim rather than minting its own; if omitted, it mints a fresh
  one itself via `idgen.service.generate_id(APPLICATION_ID_PREFIX,
  APPLICATION_ID_LENGTH)`. Resolves `customer_id` via the **read-only**
  `customer.service.find_by_identifier(applicant_identifier)`, validates
  `payload` against `product_type`'s schema, calls
  `document.service.check_completeness(...)` (with
  `exclude_categories=[CATEGORY_GOVERNMENT_ID]` when
  `reuse_existing_id_photo=True` and the applicant both resolves to a
  customer and `document.service.has_id_photo(customer_id)` is `True`).
  Converts `amount` to `float` before calling
  `workflow.service.start_workflow(...)` — see the money-type note
  under "Conventions" above. Never calls `workflow.service` when
  documents are missing.
- **`resubmit_application` does not take `reuse_existing_id_photo`** —
  deliberately deferred, see `PRD.md` §11.
- **`list_for_applicant` takes `applicant_identifier`, not
  `customer_id`** — this has to return an applicant's own applications
  even before any of them are approved and `customer_id` gets resolved.
  A `query_id` minted for one `applicant_identifier` must be
  rejected/ignored if reused with a different one — this is the actual
  mechanism enforcing "a customer only ever sees their own
  applications" (PRD §10 success criterion 2), not a UI-level filter.
- **`check_decision_allowed` resolves `customer_id`, then calls
  `account.service.has_active_account_of_type(customer_id,
  product_type)`** — both read-only. Resolves via
  `customer.service.find_by_identifier(...)` when the row's own
  `customer_id` is still `NULL`, not just trusting the column (a
  since-approved sibling application under the same identifier may have
  already resolved one). `bff_backoffice` calls this before signaling a
  single-item Approve decision; see `CLAUDE.md`'s "Applying without
  being a customer yet" for the full active-account rule, including its
  accepted, narrower (cross-request only) race-window gap.
- **`wait_for_status_change`** polls until `status` no longer equals
  `previous_status` or times out — `bff_backoffice` calls this right
  after `workflow.service.signal_decision()`/`bulk_signal_decision()`,
  which only confirm Temporal *accepted* the signal, so a route that
  immediately re-renders the affected row(s) needs the actual
  post-decision state. Always returns the current `Application`, even
  on timeout.

### `application/activities.py` — the Temporal activity contract

Not called directly by any BFF — invoked by `workflow/workflows.py`
**by string name** (see `CLAUDE.md`'s "Breaking the cycle"). **This is
also the one file in `application/` allowed to import `customer/`,
`account/`, and (for one call only) `notifications/`** — see
`CLAUDE.md`'s "Applying without being a customer yet".

```python
@activity.defn
async def persist_application(inp: PersistApplicationInput) -> None: ...
    # INSERTs the applications row -- first step of run().

@activity.defn
async def persist_decision(inp: PersistDecisionInput) -> str: ...
    # returns the status ACTUALLY written -- see the conflict-to-
    # REJECTED note below. workflows.py's submit_decision uses this
    # return value (not its own pre-computed resulting_status) for
    # self._status.

@activity.defn
async def persist_resubmit(inp: PersistResubmitInput) -> None: ...
    # sets status back to PENDING_UNDERWRITING, updates payload
```

```python
@dataclass
class PersistApplicationInput:
    application_id: str
    workflow_id: str
    product_type: str
    payload: dict[str, Any]
    amount: float
    applicant_identifier: str
    applicant_name: str
    applicant_email: str
    applicant_phone: str
    customer_id: str | None = None

@dataclass
class PersistDecisionInput:
    application_id: str
    actor_role: str        # underwriter | manager | customer
    decision: str           # APPROVE | REJECT | REQUEST_MORE_INFO | CANCELLED
    actor_name: str
    comment: str
    resulting_status: str
    decided_at: datetime | None = None  # set only for a native Temporal cancel

@dataclass
class PersistResubmitInput:
    application_id: str
    payload: dict[str, Any]
```

`persist_decision` handles all four decision outcomes
(APPROVE/REJECT/REQUEST_MORE_INFO/CANCELLED) in one activity, writing
`underwriter_name`/`underwriter_comment`/`underwriter_decided_at` or
`manager_name`/`manager_comment`/`manager_decided_at` depending on
`actor_role` — same activity, column choice branches on the argument.

**When `resulting_status == "APPROVED"`** (a terminal approval — the
Underwriter's below-threshold approve, or the Manager's approve after
escalation; *not* the intermediate `PENDING_MANAGER_APPROVAL` step),
`persist_decision` additionally:

1. Calls `account.service.get_by_application_id(application_id)`. A
   non-`None` result means this is a Temporal retry of an
   already-provisioned application — skip straight to the final write
   below, using the existing account's `customer_id`.
2. If `applications.customer_id` is still `NULL`, calls
   `customer.service.get_or_create(applicant_identifier, name, email,
   phone) -> Customer`; otherwise calls
   `customer.service.update_profile(customer_id, name, email, phone)`.
3. Calls `account.service.create_account(customer_id, product_type,
   application_id) -> Account`. **If this insert hits the
   one-active-account-per-product-type unique constraint** (the
   accepted race window was actually hit), `persist_decision` catches
   the specific `UniqueViolationError` and converts the whole decision
   into a clean `REJECTED` write instead of letting the exception
   propagate — see `CLAUDE.md`'s "Known gaps" for the full mechanism.
4. On success, calls (in order) `document.service.tag_application_documents(...)`,
   `document.service.promote_government_id_to_customer_photo(...)`,
   `document.service.generate_welcome_letter(...)`, and
   `notifications.service.send_welcome_letter_email(...)` (the fourth
   call, built Phase 19) — all four skipped, permanently, on a retry
   that finds the account already provisioned (step 1).
5. Writes `status`, the decision columns, and `customer_id` (`COALESCE`d
   — harmless if already set). There is no `account_id` column on
   `applications` to write.
